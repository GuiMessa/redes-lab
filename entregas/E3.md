# Entrega 3 — O serviço não pode cair

## O que está em jogo

<walkthrough-tutorial-duration duration="70"></walkthrough-tutorial-duration>

Até aqui a rede tinha uma máquina para cada função. Agora o mesmo serviço roda
em **três** máquinas ao mesmo tempo, e quem usa não deveria perceber quando uma
delas some. Isso é o que a disciplina chama de *transparência* — e é a razão de
existir de um sistema distribuído.

**Vale 1,2** · **Prazo: semana 11**

## Suba e derrube

```bash
make up E=3 && make verificar E=3
```

O roteiro testa o serviço em cinco estados: tudo no ar, uma réplica parada,
duas paradas, uma **partição de rede**, e tudo restaurado.

Repare na diferença entre os dois últimos tipos de falha:

* `docker stop` — a réplica **morre**. Some do mundo.
* `docker network disconnect` — a réplica **continua viva**, processando,
  achando que está tudo bem. Só ninguém consegue falar com ela.

O segundo caso é o que torna sistemas distribuídos difíceis: quem chama não
tem como saber se o outro morreu ou se apenas ficou incomunicável.

## Sua tarefa

<walkthrough-editor-open-file filePath="e3-replicas/cliente.sh">
abrir o cliente.sh
</walkthrough-editor-open-file>

O cliente que vem no laboratório fala com **uma** réplica fixa. Pare essa
réplica e o serviço "cai" — mesmo com duas outras funcionando perfeitamente.

Reescrevam o `cliente.sh` para cumprir este contrato:

* enquanto **sobrar pelo menos uma** réplica alcançável, ele responde o nome
  dela e termina com código 0;
* quando **nenhuma** estiver alcançável, ele escreve `INDISPONIVEL` e termina
  com código 1;
* em qualquer situação, ele termina em **menos de 5 segundos**.

O terceiro item é o que separa um cliente bom de um cliente ruim. Um cliente
que fica pendurado esperando resposta trava quem chamou ele, que trava quem
chamou aquele — é assim que a queda de uma máquina derruba um sistema inteiro.
Use `curl -m` e pense em quanto tempo faz sentido esperar cada réplica.

## Prove

```bash
make verificar E=3
```

O roteiro também recusa uma armadilha comum: se o cliente responder
`replica1` quando a réplica 1 está parada, isso conta como **erro**, não como
acerto. Responder rápido e errado é pior que demorar.

## Entregue

```bash
make evidencias E=3
git add -A && git commit -m "Entrega 3" && git push
```

No `README.md`, respondam: *o cliente de vocês consegue distinguir uma réplica
morta de uma réplica particionada? Se não consegue, isso é um problema?*

## Como é corrigido

| O quê | Pontos |
|---|---|
| `make verificar E=3` verde nos cinco estados | 0,5 |
| O cliente nunca passa de 5 s, nem com tudo fora | 0,2 |
| O cliente nunca anuncia uma réplica que não respondeu | 0,2 |
| Resposta escrita sobre morte × partição | 0,3 |
